B0 – Terraform Resource Identity

1. Problem with count

The original Terraform configuration uses count to create S3 buckets based on the position of landlord accounts in a list.

When the middle account la-002 is removed, the indexes of the remaining accounts shift.

For example:

Index [0] continues to represent la-001.

Index [1] changes from la-002 to la-003.

Index [2] changes from la-003 to la-004.

Index [3] becomes unnecessary and is planned for destruction.

Terraform identifies resources by their numeric index rather than their business identity. Consequently, removing one account can cause unintended replacement and destruction of other landlord buckets.

2. Why is this dangerous?

Each bucket contains landlord-specific media. Unintended replacement or destruction can result in data loss, application downtime, broken references and additional recovery costs.

This is particularly risky in a multi-tenant platform because infrastructure belonging to one landlord should not be affected by changes to another landlord.

3. Recommended solution: for_each

Use for_each with the landlord account ID as a stable resource key.

resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)

  bucket = "haven-media-${each.key}"

  tags = {
    landlord_account_id = each.key
  }
}

Terraform now identifies buckets using addresses such as:

aws_s3_bucket.landlord_media["la-001"]

aws_s3_bucket.landlord_media["la-002"]

aws_s3_bucket.landlord_media["la-003"]

aws_s3_bucket.landlord_media["la-004"]

Removing la-002 affects only its corresponding resource address. The other landlord buckets retain their identities.

4. Existing state migration

For existing resources managed using count, an explicit state migration is required when switching to for_each.

In this implementation, Terraform moved blocks map the existing numeric resource addresses to their corresponding landlord account IDs. This preserves existing resource identity and prevents unnecessary resource recreation.

The migration is verified using:
terraform plan -refresh=false

5. Validation result

The Terraform configuration was validated successfully.

The final plan showed:
Plan: 2 to add, 0 to change, 0 to destroy.

The four existing landlord buckets were recognized at their new keyed addresses, without unnecessary replacement or destruction.

No infrastructure changes were applied during the assessment.
