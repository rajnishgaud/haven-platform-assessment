# B0 — The `count` trap

With the original list `["la-001", "la-002", "la-003", "la-004"]`, Terraform addresses the buckets by numeric position:

- `landlord_media[0]` → `la-001`
- `landlord_media[1]` → `la-002`
- `landlord_media[2]` → `la-003`
- `landlord_media[3]` → `la-004`

If `la-002` is removed from the middle, the new configuration becomes
`["la-001", "la-003", "la-004"]`. Terraform still matches resources by their numeric
addresses, not by the landlord ID embedded in the bucket name. The plan therefore proposes
replacement of the buckets at indexes 1 and 2 (their bucket names change, and an S3 bucket
name is replacement-sensitive), plus destruction of the old index 3 bucket. Index 0 remains
unchanged. In effect, the plan can destroy/recreate buckets for `la-002`, `la-003`, and
`la-004`, even though only `la-002` was removed.

This is dangerous because the positional identity no longer represents business identity.
A harmless list edit can schedule destruction of buckets containing other landlords' media,
cause data loss or downtime, and trigger expensive recovery or migration work. Review the
plan carefully; do not apply the positional cascade.

**Fix:** use `for_each` keyed by the stable landlord account ID, so Terraform addresses each
bucket by business identity rather than list position:

```hcl
variable "landlord_accounts" {
  type    = set(string)
  default = ["la-001", "la-002", "la-003", "la-004"]
}

resource "aws_s3_bucket" "landlord_media" {
  for_each = var.landlord_accounts

  bucket = "haven-media-${each.key}"

  tags = {
    landlord_account_id = each.key
  }
}
```

With `for_each`, removing `la-002` affects only
`aws_s3_bucket.landlord_media["la-002"]`; the addresses for the other landlords remain
stable. For already-managed count resources, plan and perform an explicit state migration
(`terraform state mv` from each numeric address to its keyed address) before applying the
refactor. Do not assume changing `count` to `for_each` automatically preserves state.
